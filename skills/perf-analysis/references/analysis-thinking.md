# 性能分析思维框架

从需求、约束、质量属性推导性能判断的框架。用于任何性能任务开始前的定向：明确目标再设计，交叉检查审查时，技术选型前定位。

## 功能需求结束、质量属性开始的地方

需求分两类。**功能需求**说系统做什么：处理订单、搜索、发消息。**质量属性**说做得多好：多快、多可靠、多便宜、多安全。

功能需求通常有标准答案。要个推理服务？实现在公司间几乎无差异。质量属性几乎是纯权衡且无标准答案——这是性能判断真正所在。相同功能下，「百毫秒响应 + 零丢失 + 十亿用户」与「内部工具够用就行」导向完全不同的架构。

功能需求通常显式、写在产品文档里。质量属性通常隐含；很少人主动说系统必须服务多少用户或哪些数据绝不能丢。所以每当看到「什么」，立即追问「多好」：

- 多少人？百人还是十亿？
- 多快够？即时，还是三秒加载可接受？
- 数据活多久？永久，还是七天过期？
- 失败时怎样？丢一点数据无所谓，还是一条都不能丢？

这些问题的答案是性能分析的真正输入。只看功能不看质量属性会产出错误的方案。

## 判断循环

性能判断是循环，不是一次性流水线：

需求 → 约束 → 质量目标 → 候选方案 → 权衡 → 决策

业务变化或规模变化时，约束与质量目标随之移动；昨天的最优可能不再最优，循环重启。性能必须演进的原因是这个循环永不停止。

## 约束先于方案

约束是设计不可越过的边界。与质量属性的区别：质量属性是追求的目标；约束是给定条件。

| 约束 | 如何收窄选项 |
| --- | --- |
| 团队规模 | 架构复杂度不能超过团队可运维的。三人团队跑几十个微服务会淹没在运维里 |
| 时间 | 下周交付 vs 一年跑道迫使完全不同的方案。时间压力下选现在能交付的，不选理论最优 |
| 预算 | 决定机器、服务、人力。买不起的优雅方案是空谈 |
| 合规 | 数据驻留要求之类的红线。违反则设计作废；无权衡空间 |
| 既有系统 | 多数设计不从零开始；它们适配已有的接口与脾气 |
| 第三方依赖 | 外部网关或云服务的能力上限与失败成为你的上限 |

约束是帮手，不是障碍。没有约束，设计问题有无限选项且无处着手；知道是三人团队、三个月、must-pass 合规立即杀死多数花哨选项。在画任何东西之前先映射约束，你通常能击败立即开始画的人——更快且更稳。

## 质量属性检查清单

给定系统，逐项走这个清单。每项问两个问题：它对本系统重要吗，目标是什么？多数项评级低本身是重要信息——它告诉你不要过度工程。

| 质量属性 | 如何测量 | 典型杠杆 | 主要冲突于 |
| --- | --- | --- | --- |
| 性能 | 延迟（一次调用多久）、吞吐（每秒多少次）；看 P99 不看平均 | 缓存、读写分离、异步、索引 | 成本、一致性、简单性 |
| 可用性 | 几个九；对应每年允许停机时间 | 冗余、消除单点、故障域隔离、优雅降级 | 成本、一致性 |
| 可扩展性 | N 倍负载是否通过加资源平滑吸收 | 无状态设计、水平扩展、复制、分片 | 一致性、简单性、成本 |
| 一致性 | 在强到最终一致性谱上的何处 | 事务与协调协议（强）；异步复制（最终） | 性能、可用性、可扩展性 |
| 安全 | 攻击面；最坏情况损失 | 不信任输入、最小权限、纵深防御、数据分级 | 性能、便利、成本 |
| 可维护性 | 一个变更多久；新人多快上手 | 清晰边界、低耦合、可观测性、记录决策 | 极端性能、短期交付速度 |
| 成本 | 单位成本：每用户、每请求、每订单 | 反向的预算，封顶其他属性的目标 | 与几乎所有冲突 |

成本值得单独强调：它是最被忽视的属性且常是真约束。冗余花钱，缓存花钱，强一致性花钱因为它难扩展。低效设计在万用户时烧几百元/月——没人注意——在亿用户时每月数百万，同一缺陷被规模放大。把多数架构争论剥到底，争的不是技术上是否可能，而是钱和人是否值得。

## 没有银弹，只有权衡

几乎每个让系统在一方面更好的选择都让它在另一方面更差：

- 更快通常花钱（更多缓存、更多机器）或一致性（过期读）
- 更强一致性通常花性能与可用性（等所有节点）
- 更高可扩展性通常花简单性（分布式复杂度）
- 更快交付通常花可维护性（技术债）

由此产生几乎通用的试金石：**如果方案被描述为各方面都更好且无缺点，方案不是完美的——思考未完成。** 想透的人能说出选项买什么、牺牲什么、为何牺牲值得。评估别人设计或自己设计时，先找权衡；找不到就怀疑思考未完成再相信完美。

## 六个锚定问题

质量属性与约束多是隐含的；必须问出来。这些问题适合几乎任何系统，每个锚定一类决策：

1. **什么规模？** 今天的用户与数据、峰值负载。决定是否准备扩展。
2. **读写比？** 读重还是写重。决定优化哪边，塑造数据存储方式。
3. **一致性要求？** 刚写的值必须立即读回吗；能容忍多长不一致窗口。经典权衡点。
4. **增长预期？** 一年后规模在哪；稳定还是尖峰。决定留多少扩展空间。
5. **失败代价？** 停机或数据丢失多糟。决定可靠性投资。
6. **什么约束？** 团队、时间、预算、合规。选项空间的边界。

没有最佳架构，只有这组答案下最合适的。同一聊天功能对三人内部工具和十亿用户产品有完全不同答案；区别不是工程师技能而是六个问题的不同答案。答案变化时，最优移动。

## 示例：三个功能生成质量目标表

需求：URL 短链——长 URL 变短码，点击重定向，可能要点击统计。

只三个功能，几乎无设计空间。问六个问题：

- 规模：中型服务，每天千万新链接。
- 读写比：链接创建一次、点击无数次；100:1 甚至 1000:1。
- 一致性：链接创建后一两秒可达是可容忍的。
- 增长：链接永久累积。
- 失败代价：重定向坏了伤体验但不致命；丢失映射让每条分享链接失效——灾难。
- 约束：小团队、快交付、有限预算。

把答案转译为质量目标：

| 属性 | 目标 | 从哪个答案 |
| --- | --- | --- |
| 读延迟 | 重定向 50ms 内 | 偏读比；重定向是核心体验 |
| 读可扩展性 | 吸收巨量读流量 | 峰值在读 |
| 持久性 | 短链映射绝不能丢 | 丢失让每条分享链接失效 |
| 一致性 | 最终即可 | 一两秒延迟可容忍 |
| 成本 | 存储必须便宜 | 数据永久累积在有限预算下 |

这张表是后续每个决策的依靠。哈希码（简单，但处理冲突）还是全局序列服务（干净，但新增活动件）；用缓存吸收读（快；代价是过期数据——一旦最终一致性确认就可接受）；映射存键值库（访问形态是简单键查找）。每个决策追溯到六个问题的某个答案。这是架构判断与「就挑了个数据库」的区别。

## 向业务解释权衡

权衡排序属于理解业务的人。把技术选择转译为钱、风险、交付日期——不是技术参数：

- 总给选项附成本，不只给结论。列出路径 A 与路径 B 各自获得什么、放弃什么、花费多少、多久，让业务知情选择。
- 用三种货币报价：钱、风险、时间。几乎任何技术权衡都转换为这些。
- 把质量属性系于业务指标。不是「四个九可用性」而是「按我们平均订单价值，停一小时成本约这么多，所以可用性值这个钱」。
- 分离底线与锦上添花。安全合规与钱正确性通常不可协商；延迟从 200ms 削到 100ms 可能是打磨。把所有都叫同等紧急会摧毁你的可信度。

## 品味：在可辩护选项间选对的

框架收敛到几个候选都听起来合理；在它们间选需要品味。品味不是神秘主义；它有可操作面向：

- **架构无标准答案。** Fowler 论证从单体开始；Tilkov 在同一站论证不从单体开始；Stack Overflow 用单体加几台服务器每天服务两亿请求；Netflix 跑几百微服务。两者都成功——区别是约束。因此铁律：复制别人架构而不复制他们约束是灾难。
- **简单优先于熟悉。** 简单（无纠缠结构）不等于容易（快速上手）。选已经知道的常制造后续付出的复杂度。看到设计时问如何能更简单，不问能加什么。
- **不追潮流。** Amazon Prime Video 把视频质量监控从微服务与 Serverless 回迁单体并砍约 90% 成本（Prime Video Tech, 2023）；Segment 合 140+ 微服务回单体，把半天停机部署变一个工程师分钟级工作（Segment engineering blog "Goodbye Microservices", 2020-07）。教训不是微服务错——是跟风错。当所有人喊一个词时，只问它是否适合当前约束、能否付得起代价。
- **节约创新。** 每个团队持有有限创新 token；每个不成熟新技术花一个去踩无人映射的坑。用无聊、成熟、可预测技术构建系统压倒性大块；只在真正差异化点冒险。
- **知道规则再破。** 「不要过早优化」是好规则，但当读路径已知在发布时熔化，提前留缓存接缝是合理例外。危险不是例外；是破从未理解的规则。
- **小团队默认偏克制。** 少人、紧期限、有限预算、负载远未全球弹性：偏向单体、无聊技术、对复杂度过敏。只在约束实际变化时转向分布——到那时你知道如何转。

练习感受复杂度痛苦：加任何组件、服务、抽象层前，回答「没它会死吗？」如果什么都不死，暂时别加。
