# 测量质量

性能测量中的误差来源、实验设计、统计有效性判断。benchmark 协议规定了记录什么；本文解释为什么那样记录、如何避免测量伪影、如何判断差异是真实的还是噪声。

## 适用信号

- 设计测量方案时，需要理解误差来源
- 解读 benchmark 结果时，判断置信度
- 对比两次测量时，判断差异显著性
- 审查性能报告时，检查实验质量

## 核心模型

性能测量值 = 真实值 + 系统性偏差 + 随机噪声

**系统性偏差**：测量方法本身引入的固定偏移（冷启动、客户端瓶颈、计时器精度）。多次运行不能消除，需要设计消除。

**随机噪声**：每次运行的不可预测波动（调度、后台任务、硬件状态）。多次运行可通过统计量化，但不能消除到零。

## 主要误差来源

### 1. 冷启动 vs 稳态

**现象**：首次请求比后续慢 10-100 倍。

**原因**：模型加载、JIT 编译、缓存预热、连接池建立。

**处理**：
- warmup 阶段：发足够请求让系统进入稳态（观测延迟稳定），丢弃 warmup 数据
- 分别测量冷启动与稳态，不混合报告
- 声明测的是哪个

**常见误判**：把包含冷启动的测量当稳态吞吐

### 2. 时钟与采样精度

**现象**：亚毫秒操作测出来都是 0ms 或 1ms。

**原因**：系统时钟精度（Linux 默认 1ms，Windows 可能 10-15ms）；计时器本身开销。

**处理**：
- 微秒级操作：重复 N 次取总时间除以 N，或用高精度计时器（`clock_gettime(CLOCK_MONOTONIC)`、`QueryPerformanceCounter`）
- 纳秒级：硬件性能计数器（`perf`、`rdtsc`）
- 声明计时器类型与精度

**常见误判**：把精度不足的测量当真实分布

### 3. 背景负载与资源竞争

**现象**：同一测试不同时间跑结果差 2-5 倍。

**原因**：其他进程、系统服务、定时任务、网络流量、共享机器上的其他租户。

**处理**：
- 理想：专用机器、关闭不必要服务、固定 CPU 绑核
- 现实：多次运行、报告方差、标注共享环境
- 对比时保持环境一致

**常见误判**：单次运行下结论

### 4. 热节流（Thermal Throttling）

**现象**：长时间测试中性能逐步下降 10-30%。

**原因**：GPU/CPU 温度达阈值，自动降频保护硬件。

**处理**：
- 监控温度与频率（`nvidia-smi dmon`、`watch -n1 cat /proc/cpuinfo`）
- 冷却间隔：测试间等待温度回基线
- 改善散热或接受节流作为真实工况
- 报告是否出现节流

**常见误判**：把节流后的低性能当稳定状态

### 5. 数据生成偏差

**现象**：测试数据上快，真实数据上慢。

**原因**：
- 测试数据过于规整（固定长度、单一模式、缓存友好）
- 真实数据有长尾、罕见模式、缓存未命中
- 输入 token 长度分布不匹配真实

**处理**：
- 从真实流量采样或按真实分布生成
- 报告数据特征（长度分布、词表覆盖、模式种类）
- 分别测不同输入特征下的性能

**常见误判**：用 512 token 固定输入测长文本系统

### 6. 客户端瓶颈

**现象**：服务端 GPU 利用率低，延迟却高。

**原因**：
- 客户端并发不足，服务端等待
- 客户端 CPU 成为瓶颈（序列化、网络栈）
- 网络往返延迟混入应用延迟

**处理**：
- 分离网络 RTT 与服务端处理时间
- 增加客户端并发到服务端利用率饱和
- 用多台客户端或异步发送
- 服务端埋点分离各阶段

**常见误判**：把端到端延迟当服务端处理时间

### 7. 缓存效应

**现象**：第二次跑比第一次快 10 倍。

**原因**：文件系统缓存、KV cache 预填充、权重常驻显存。

**处理**：
- 声明缓存状态（cold / warm / hot）
- 测试前清缓存（`sync; echo 3 > /proc/sys/vm/drop_caches`）或预填充
- 分别测各缓存状态
- 真实工况往往是 warm

**常见误判**：把 hot cache 当 cold 报告

## 统计有效性

### 样本数

**最低要求**：
- 延迟：至少 3 次独立运行，报告中位数与 P95/P99
- 吞吐：至少 5 次独立运行（每次足够时长达稳态），报告均值与标准差
- 微观 benchmark（单操作）：至少 10 次

**判断是否足够**：
- 计算变异系数 CV = 标准差 / 均值
- CV < 5%：样本足够
- CV 5-10%：边缘可接受，增加样本更好
- CV > 10%：噪声过大，增加样本或改善环境

### A/B 对比的显著性

改动后性能变化是真实的还是噪声？

**简单判断**（适用于样本数少、非专业统计）：
1. 两组各至少 5 次运行
2. 画箱线图或列出各次测量值
3. 两组的四分位范围（Q1-Q3）不重叠 → 差异明显
4. 重叠但中位数差 > 较小组的四分位距 → 可能有差异
5. 重叠且中位数差小 → 不确定，需更多样本或更严格统计

**正式判断**（有统计工具）：
- Mann-Whitney U 检验（非参数，适合延迟分布）
- t 检验（要求正态分布，适合吞吐均值）
- p < 0.05 视为显著，但要报告效应量（实际差异大小）

**常见误判**：
- 单次对比下结论
- 只看均值不看分布
- 差异小于测量噪声时宣称「提升 X%」

### 实际效应 vs 统计显著性

**统计显著**：差异不太可能是随机的（p 值）

**实际效应**：差异大到值得在乎吗？

示例：测 10000 次后发现延迟从 50.00ms 降到 49.95ms，p < 0.001（统计显著），但实际效应 0.1% 可忽略。

反例：测 3 次，延迟从 100ms 降到 70ms（30% 提升），但 p = 0.15（不显著）。实际效应大，但需更多样本确认。

**报告时**：同时给统计结论与效应大小。

## 正反例

### 好的测量设计

```
目标：对比量化方法 A vs B 对吞吐的影响

设计：
- 环境：单 A100-80GB，CUDA 12.1，vLLM 0.4.2，模型 Llama-2-7B
- 负载：输入 512 token，输出 128 token，并发 32（已验证饱和）
- Warmup：50 请求后开始计时
- 采集：每种方法跑 10 次，每次 500 请求
- 控制：两种方法间清 KV cache，重启服务
- 测量：服务端日志的处理时间（排除网络）

结果：
- 方法 A：均值 45.2 tok/s，标准差 1.8 tok/s，CV 4.0%
- 方法 B：均值 52.7 tok/s，标准差 2.1 tok/s，CV 4.0%
- Mann-Whitney U：p < 0.001，效应 16.6% 提升
```

清晰、可复现、控制变量、统计足够。

### 坏的测量

```
「优化后快了 3 倍」

问题：
- 没说基线环境
- 没说测了几次
- 没说负载
- 3 倍是什么指标？峰值吞吐？平均延迟？
- 可能是冷启动 vs 稳态的对比
```

不可复现、无法验证。

## 常见误判模式

1. **「理论上能达到」**：计算出的峰值当实测结果
2. **单次运行当结论**：忽略随机噪声
3. **混合冷启动与稳态**：把瞬态当常态
4. **改多个变量**：同时改模型、batch size、量化方法，无法归因
5. **客户端瓶颈误判服务端慢**：端到端延迟全算服务端
6. **精度不足当零开销**：亚毫秒操作测成 0ms
7. **不报方差**：只报均值或单次峰值
