# 完整分析：性能

重型的系统性性能审查。**仅用户显式触发**，不自行进入。分阶段阅读，高严重度结论自我复核。

## 触发

用户明确说「完整分析」「系统性性能审查」「全面 profiling」。

## 步骤

### 1. 上下文登记

动笔前写下：审查目标（哪个子系统/哪个指标）、必读（配置、启动参数、日志）、可选上下文（相邻代码、历史调优记录）、待解问题。

### 2. 基线审计

检查既有基线是否合格（见 SKILL.md 参考文档导航表 benchmark-protocol）：负载定义、环境记录、统计口径、样本数。不合格的基线不能作为对比锚点，先补测（需授权）。

### 3. 分层剖析

自顶向下逐层收敛，每层记录证据：

1. 服务级：吞吐/延迟/错误率的总体形态（饱和、抖动、退化曲线）。
2. 引擎级：调度、批组成、队列、缓存命中形态（按引擎提供的指标）。
3. 算子/内核级：profile 数据（nsys / ncu / 引擎自带 profiler，按可用性选择）。
4. 资源级：GPU 利用率、显存带宽、通信、功耗、内存交换。

只在上一层证据指向下层时下探；不做无指向的全量剖析。

### 4. 假设-验证循环

每个候选瓶颈作为一个假设：写出预期信号 → 检查证据或设计最小验证 → 记录结果。未验证的假设保留为假设，不得升级为结论。

### 5. 自我复核

每个高严重度结论：重读证据、考虑合理解释（是否故意配置？是否测量伪影？是否混杂变量？），写明置信度。经不起复核的降级或删除。

### 6. 改动建议与授权

建议直接报告；执行修改（参数、配置、版本变更）需另行明确授权。跨多文件的改动给计划与成本，由用户决定。

## 输出格式

```text
结论
- [严重度, 置信度] 主题
  证据: 支持证据与反证，剩余不确定性
  判断: 机制解释
  建议: 最小充分改动 + 预期收益区间 + 验证方法 + 回退方案

测量记录
- 已有基线的合规性判定；本次补测的环境/负载/统计（引用归档路径）

待验证假设
- …（含验证草案）

待用户决定
- …
```

## 停止规则

- 未验证假设不写成结论；单变量原则下的归因才有效。
- 不自动执行有负载命令或环境变更。
- 证据不足时说不足，不包装成确定。
