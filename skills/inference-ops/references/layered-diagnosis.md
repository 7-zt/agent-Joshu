# 分层诊断

硬件→驱动→系统→容器→依赖→服务→应用的逐层排查方法，配套的复现与二分技术、解决回退与收尾标准。三部分连成一个完整排障闭环：定位 → 验证 → 解决。

## 一、层次模型与检查清单

```
应用层      │ 业务逻辑、配置错误、资源耗尽
  ↓
服务层      │ 启动失败、端口占用、健康检查
  ↓
依赖层      │ 包版本冲突、导入失败、库不兼容
  ↓
容器/运行时 │ 镜像问题、volume、网络、权限
  ↓
系统层      │ OS配置、文件系统、进程限制
  ↓
驱动层      │ CUDA/驱动版本、加载失败
  ↓
硬件层      │ GPU可见性、内存、PCIe
```

### 判断顺序

**自底向上**（推荐默认）：从硬件开始逐层向上，每层健康才进入上层。适合：无明确报错、新环境、首次部署。

**自顶向下**（有明确信号时）：从报错信号直接定位层次，快速收敛。适合：有清晰错误信息。

**夹逼**（复杂问题）：同时从两端检查，找到断裂层。

### 每层检查清单

**硬件层**（L0 命令）：

```bash
nvidia-smi  # GPU可见性与状态
lspci | grep -i nvidia  # PCIe设备
free -h  # 内存
df -h  # 磁盘
```

健康标准：GPU 被 OS 识别、无硬件错误、显存/内存充足。常见问题：GPU 不可见、PCIe 降速（x8 vs x16）、显存 ECC 错误。

**驱动层**：

```bash
nvidia-smi  # 驱动版本
cat /proc/driver/nvidia/version
nvcc --version  # CUDA版本
```

健康标准：驱动版本与 CUDA 兼容、能查询 GPU 信息、无驱动崩溃日志。常见问题：driver mismatch、CUDA runtime 与驱动版本不匹配、驱动未加载。

**系统层**：

```bash
uname -a  # OS版本
ulimit -a  # 进程限制
dmesg | tail -50  # 内核日志
journalctl -xe  # 系统日志
```

健康标准：无 OOM killer 记录、文件描述符限制足够、无 SELinux/AppArmor 阻止。常见问题：ulimit 过低、权限不足、内核 OOM。

**容器/运行时层**：

```bash
docker --version / podman --version
docker inspect <container>
docker run --rm --gpus all nvidia/cuda nvidia-smi  # GPU容器测试
（具体以当前 NVIDIA Container Toolkit 版本文档为准）
```

健康标准：NVIDIA Container Toolkit 安装、GPU 在容器内可见、volume 正确挂载。常见问题：runtime=nvidia 未配置、volume 路径错误、网络隔离。

**依赖层**：

```bash
python --version
pip list | grep <关键包>
pip show <包名>  # 详细版本与依赖
python -c "import torch; print(torch.cuda.is_available())"
```

健康标准：Python 版本匹配、关键包已安装且版本兼容、能导入核心库。常见问题：版本冲突、缺少依赖、ABI 不兼容。

**服务层**：

```bash
ps aux | grep <服务名>
netstat -tuln | grep <端口>
curl localhost:<端口>/health
systemctl status <服务>  # systemd服务
```

健康标准：进程运行、端口监听、健康检查通过。常见问题：启动失败、端口被占用、配置文件错误。

**应用层**：应用日志、配置参数、业务逻辑错误。

### 停止条件

- **找到断裂层**：某层不健康，下层健康 → 锁定该层。
- **全层健康但问题仍在**：可能是负载、时序、外部依赖问题。

具体故障域的深入检查（依赖/容器/资源耗尽）见 [deploy-common-causes](./deploy-common-causes.md)。

## 二、复现与二分

### 最小化复现

**目标**：找到能稳定触发问题的最小条件集。

**步骤**：记录当前完整复现路径 → 逐项移除组件/步骤 → 每次移除后测试是否仍复现 → 保留所有必要项，移除所有非必要项。

**示例**：

```text
初始：多用户、复杂配置、大模型、长序列 → 失败
移除：单用户 → 仍失败
移除：简化配置 → 仍失败
移除：小模型 → 不失败了
结论：与模型大小相关，其他无关
```

**价值**：排除干扰因素、加快验证速度、明确根因范围。

### 复现率统计

不稳定复现：测试 N 次，记录成功/失败次数，计算复现率，报告「10 次中 8 次复现（80%）」。触发条件分类：首次启动必现 vs 运行一段时间后、特定输入 vs 随机输入、高负载 vs 低负载。

### 变更历史二分（Git bisect 风格）

**适用**：「之前好的，现在坏了」。

**步骤**：确认好版本（last known good）与坏版本（first known bad）→ 二分查找中间版本 → 测试 → 根据结果调整区间，重复。

**示例**：

```text
v1.0（好）─────v1.5─────v2.0（坏）
            测试v1.5 → 坏
v1.0（好）───v1.2───v1.5（坏）
          测试v1.2 → 好
         v1.2（好）─v1.3─v1.5（坏）
                 测试v1.3 → 坏
                锁定：v1.25 附近引入问题
```

**配置/环境二分**：对比好环境与坏环境配置，逐项同步配置项，找到导致问题的差异。

### 对照实验

对照组（好环境/版本）与实验组（坏环境/版本），单变量：只改一个疑似因素。在对照组引入变化 → 能否复现问题；在实验组移除变化 → 能否消除问题。两个方向都验证，增强置信度。

## 三、解决、回退与收尾

### 方案分级

**Workaround（临时方案）**：绕过问题而非解决根因；可能有副作用或限制；需要后续根本解决。示例：OOM → 降低 batch size（治标不治本）；端口冲突 → 换端口（未清理占用进程）。记录要求：明确标注「临时方案」、说明适用条件与限制、给出触发根本解决的条件。

**根本解决**：消除根因；无副作用或可接受代价；通过验证。验证方法：原始复现路径不再触发、压力测试稳定、监控指标恢复正常。

### 执行前准备

**回退方案**（每个变更必须有）：

```bash
# 配置变更：备份 → 变更 → 可回退
cp config.yaml config.yaml.backup.$(date +%Y%m%d_%H%M%S)
vim config.yaml
cp config.yaml.backup.YYYYMMDD_HHMMSS config.yaml  # 回退
```

- 服务重启：确认服务管理方式（systemd/supervisor/docker），测试回退命令可用。
- 版本变更：记录当前版本号，准备降级命令。

**变更窗口**：高风险变更选择低峰时段、准备监控、有人值守。

### 验证标准

- 功能验证：原始故障场景不再复现、核心功能正常、健康检查通过。
- 性能验证：延迟/吞吐恢复正常、资源使用在预期范围、无新的异常告警。
- 回归验证：其他功能未受影响、相关系统正常。

### 问题闭环

- 文档更新：新的配置参数、监控指标、已知问题写入运维文档；症状→根因→解决方案写入排障文档，避免重复排查。
- 监控改进：加能早期发现此类问题的指标与告警阈值。
- 根因消除：临时方案计划升级时间并跟踪；系统改进（配置校验、自动化检查、资源预留）。

### 报告模板

```markdown
## 问题总结
- 故障现象 / 影响范围 / 持续时间

## 根因
- 定位过程简述 / 根本原因 / 为何发生

## 解决方案
- 采取的措施 / 是否根本解决 / 如为 workaround，说明限制

## 验证结果
- 复现路径验证 / 功能验证 / 性能验证

## 后续行动
- 监控改进 / 文档更新 / 根本解决计划（如适用）
```
