# 问题报告（Issue Report）

记录发现的问题、bug、异常行为。**只记事实，不做分析**。报告供后续独立任务（排查、修复、评审）消费。

## 核心原则

事实与分析分离：报告阶段只记录可观测事实；定位、根因、方案留给后续任务。这防止过早收敛、减少认知偏差、保持报告客观。

## 报告模板

```markdown
# 问题：<简短描述性标题>

**报告时间**：YYYY-MM-DD HH:MM
**报告人**：<姓名或标识>
**严重程度**：<Critical/High/Medium/Low/待评定>（评定人 + 依据；不确定就写「待评定」）
**问题类型**：Bug / Performance / Deployment / Documentation / Other

## 当前状况
- 观测到的现象（何时、何地、影响范围），只描述不解释。

## 预期行为
- 期望的正确行为。

## 复现步骤
1. …
**复现情况**：<每次 / 偶尔（约 x/y 次）/ 仅一次 / 未尝试复现>

## 环境信息
- 来自实际命令输出的版本信息。常用采集命令：
  - 硬件：`nvidia-smi` (GPU)、`lscpu` / `cat /proc/cpuinfo` (CPU)、`free -h` (内存)
  - 操作系统：`uname -a`、`cat /etc/os-release`
  - 软件版本：`python --version`、`pip show <包名>`、`<引擎> --version`
  - 容器：镜像 digest、docker/podman 版本
- 可裁剪，无关项写「不适用」。

## 日志与错误信息
- 完整关键片段，保留时间戳与上下文；脱敏后写入。

## 已尝试的操作
- 尝试 A：<实际结果>（只记结果，不记判断）

## 附加信息
- 其他相关观测事实。
```

## 证据要求

- 只记录可观测、可重现、可验证的事实；错误信息不截断关键部分。
- 版本信息来自实际命令输出，不猜测。
- 复现步骤可操作；未尝试复现就如实写「未尝试复现」。
- 缺失信息写「待补充」，不编造。
- **绝对禁止**：推测性语言（「可能」「应该是」「估计」）、根因分析、解决方案建议、代码修改建议。

## 存储位置

默认写入本工作区的 `reports/` 目录，文件名 `YYYY-MM-DD-NN-theme.md`（NN 从 01 递增）。项目另有约定（如 `.omp/bug_reports` 或任务材料目录）时从其约定。

## 停止规则

- 不进行任何分析；不推测根因；不给方案。
- 不修改代码或配置；不自动执行排查步骤。
- 报告独立可读，不依赖会话上下文。
- 模板按问题类型可裁剪：不适用的节写「不适用」，不制造内容。
