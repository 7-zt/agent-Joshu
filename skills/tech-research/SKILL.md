# 技术调研（Tech Research）

结构化、证据优先的调研流程，产出可复用的学习报告。适用于：学习新推理引擎/优化技术、工具与方案对比、技术细节深挖、为决策收集证据。

## 工作流程（严格遵循）

1. **澄清调研问题**：调研什么、多深、优先角度、目的（学习/决策/对比/验证）。
2. **识别关键维度**：拆子主题、列问题清单、标背景知识。
3. **广泛探索**：先宽后深；从初步结果识别子主题与不同视角；**不让头一两个来源定义整个方向**。
4. **深度挖掘**：每个维度定向搜索；变换关键词组合；通读重要来源全文（不只摘要）；来源提到的关键资源跟进。
5. **验证与分类**：覆盖多样信息类型；多源同说视为同一证据链的一部分，整合交叉验证（警惕转载链伪装成多源）；支撑关系不清不写定论。
6. **综合输出**：结论摘要、来源清单、完整报告、未解决问题分列；事实、推断、判断、建议、待确认分开呈现。

## 来源分级

1. **一手来源**：官方文档、论文、发布页、项目源码与官方 issue、直接实验与测量结果。
2. **二手来源**：技术博客、教程、社区讨论、行业报告——只用于发现线索、补充背景、辅助对比。
3. **仅作线索**：营销材料、来源不明内容。

优先一手；二手不单独支撑结论。

## 来源快照（审计链）

重要来源**默认保存快照**：原文存为 Markdown 文件（含 URL、作者、发布日期、访问日期）。无法保存原文时，至少保存：详细摘要、关键摘录、URL、作者、发布日期、访问日期。快照归档到报告的 `sources/` 子目录，正文引用快照路径。不依赖网页当前状态做后续审计。

## 论断分类（输出中逐条标注）

- **[事实]**：可直接验证的客观陈述（版本号、API 存在性、功能特性）。
- **[推断]**：基于事实的推导，给出推理链。
- **[判断]**：主观评价或权衡（「X 更适合场景 Y」）。
- **[宣传]**：利益方的营销性陈述（「最快的推理引擎」）——引用时必须保持此标注。
- **[未解决]**：当前证据不足或冲突的问题。

## 证据要求

- 重要论断引用来源（URL + 访问日期，或文档版本/快照路径）。
- 版本相关功能与行为必须标注版本号；版本不明写「版本未确认」。
- 性能数据注明：测量环境、负载、来源、是否官方数据、是否本机复测。
- 对比结论说明对比维度与适用条件。
- 证据冲突不隐藏，记入未解决问题。

## 输出契约

```markdown
# <调研主题>
调研时间 / 调研目的 / 关键维度

## 执行摘要（3-5 段核心发现，按重要性）

## 主要发现
### <维度>
[事实]… [推断]… [判断]…
来源: [标题](快照路径或URL) - 访问日期/版本

## 对比与权衡（如适用）

## 未解决问题
1. <问题> - 原因：证据不足 / 证据冲突 / 版本不明

## 来源清单（按一手/二手/仅线索分级）

## 建议后续行动（如适用）
```

## 子代理

大型调研尽量用子代理并行收集处理；超过并发上限就排队；出错纠正优先于终止，不可恢复时保存当前状态。

## 停止规则

- 证据不足不下定论；不把二手当一手引用；不把宣传当事实。
- 完成请求范围即停止，不仅因「还有更多来源」无限扩展。
- 不编造来源；不隐藏「没找到答案」；不把推断伪装成事实。
