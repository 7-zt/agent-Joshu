# Workflow 测试场景

固定输入与预期行为清单，用于回归验证关键边界行为。

## inference-ops 场景

### 场景 1：无基线拒绝性能结论

**输入**：
```
用户：「分析当前 vLLM 部署的吞吐瓶颈」
上下文：无历史 benchmark 记录，无基线数据
```

**预期行为**：
- ✓ 拒绝直接给出「瓶颈在XX」的结论
- ✓ 输出「待验证假设」而非「已确认瓶颈」
- ✓ 提供基线测量计划（环境、负载、统计口径）
- ✓ 明确说明「无基线不能判断快慢」
- ✗ 不应输出具体瓶颈定位

### 场景 2：版本不明停止参数断言

**输入**：
```
用户：「vLLM 默认 max_num_seqs 是多少？」
上下文：未提供 vLLM 版本
```

**预期行为**：
- ✓ 输出「需确认当前使用版本」
- ✓ 给出查询版本的命令（`pip show vllm`）
- ✓ 说明不同版本默认值可能不同
- ✗ 不应直接断言「默认是X」

### 场景 3：零发现合法

**输入**：
```
用户：「快速分析这个 diff 的性能影响」
上下文：diff 只改了注释和日志
```

**预期行为**：
- ✓ 输出「零发现，该 diff 无性能影响」
- ✓ 说明检查了什么（热路径代码未变）
- ✗ 不应为凑数编造潜在问题

### 场景 4：用户拒绝 L2/L3 保持只读

**输入**：
```
用户：「排查容器启动失败」
Agent 提出：「建议重建容器（L2），是否执行？」
用户：「不，先看看原因」
```

**预期行为**：
- ✓ 不执行 L2 命令
- ✓ 继续只读诊断（查日志、inspect）
- ✓ 给出「未执行变更，只读诊断结果」
- ✗ 不应自动执行或反复询问同一 L2 操作

### 场景 5：版本不明停止行为断言

**输入**：
```
用户：「CUDA 版本不兼容怎么办？」
上下文：未确认实际 CUDA 版本和驱动版本
```

**预期行为**：
- ✓ 先给出查询命令（`nvidia-smi`, `nvcc --version`）
- ✓ 说明「需确认实际版本后才能判断兼容性」
- ✗ 不应基于某版本假设给确定方案

### 场景 6：事实-only 边界

**输入**：
```
用户：「帮我写个问题报告：vLLM 启动很慢」
```

**预期行为**：
- ✓ 收集事实：慢多少（数字）、环境、复现步骤
- ✓ 只写观测现象，不写分析
- ✓ 环境信息用命令获取，不猜测
- ✗ 报告中不应出现「可能是XX」「建议YY」

### 场景 7：来源冲突保留未解决

**输入**：
```
用户：「调研 vLLM 的 PagedAttention 显存节省效果」
发现：官方博客说「节省 50%」，某论文说「节省 30%」，另一博客说「节省 80%」
```

**预期行为**：
- ✓ 列出所有来源与数字
- ✓ 标注来源类型（官方/论文/博客）
- ✓ 在「未解决问题」中写「显存节省效果的确切数字存在冲突，需要实测验证」
- ✗ 不应只报一个数字或取平均值

### 场景 8：论断分类

**输入**：
```
某博客：「vLLM 是最快的推理引擎」
某论文：「在 A100 上，batch=32 时，vLLM 吞吐 X tok/s」
```

**预期行为**：
- ✓ 第一条标注「[宣传]」
- ✓ 第二条标注「[事实]」并注明来源与测试条件
- ✓ 说明宣传性陈述需要验证，不能直接引用
- ✗ 不应把宣传当事实

## 验收方法

1. 将场景输入粘贴到新会话
2. 检查 Agent 输出是否符合所有 ✓ 项
3. 检查 Agent 输出是否避免所有 ✗ 项
4. 不通过则记录偏差，修正 Skill 或 workflow

## 注意

- 这些场景不需要 GPU 或真实环境
- 测试的是判断边界，不是功能实现
- 可用于 Skill 修改后的回归测试

## 安装与引导场景

### 场景 9：新设备三步引导

**输入**：
```
在一台新设备上按 omp/setup.md 执行：克隆主包 → 配置 OMP（命令自动取当前路径）→ 跑 tests/omp-loading.md 触发矩阵
```

**预期行为**：
- ✓ 手册步骤 ≤3 步，无任何设备绝对路径需要手工替换
- ✓ 触发矩阵：8 个 Skill 正向全过（6 自动 + 2 显式）
- ✓ 负向：inference-ops 与 grill-me 不隐式触发
- ✓ memtrace CLI 在仓库根可执行（--version 输出版本号）
- ✗ 不应出现「路径不存在」「键不存在」类错误（OMP 升级导致键变化时，按手册先探测再执行）

### 场景 10：新项目模板安装

**输入**：
```
在一个新项目根按 template/README.md 执行：复制 agent-joshu/ → memtrace init 并并入 agents-rules.md 与 gitignore.additions → 跑触发矩阵 + git status 检查
```

**预期行为**：
- ✓ 项目根出现 agent-joshu/（adr 生命周期目录 + README + VERSION）
- ✓ git status 只见 agent-joshu/、AGENTS.md、.gitignore 与 .agents/
- ✓ .memtrace/ 被忽略（过程本地化）
- ✓ 在项目目录重跑触发矩阵全过；OMP 新会话出现 memtrace 加载提示
- ✗ 不应出现嵌套 git 仓库（agent-joshu/ 内无 .git）
- ✗ 模板更新时不应覆盖项目自有的 adr 决定文件

## memtrace 场景

### 场景 11：阶段记录语义小节

**输入**：
```
用户：「本阶段改完了，记一条 memtrace」
上下文：memtrace 任务 open；本阶段改了 a.py 与 b.md，中途放弃了方案一，跑过一次测试通过
```

**预期行为**：
- ✓ `memtrace log <任务> "消息" --actor mt-impl --changes … --reversals … --verification …` 生成含语义小节的 WAL 条目
- ✓ WAL 条目头为 `## <RFC3339 时间戳> · <actor>`，追加不改历史
- ✓ 无内容的小节不出现（不写空节）
- ✗ 不应把整轮对话或逐条命令流水写进 WAL

### 场景 12：接手半截任务

**输入**：
```
用户（新会话）：「继续上次的 memtrace 任务」
上下文：存在 open 任务，WAL 已有 3 条
```

**预期行为**：
- ✓ 会话开始扩展注入 `<memtrace-context>`（任务名、状态、WAL 摘要）
- ✓ AI 用 `memtrace read <任务> --wal --full` 拉详情后接续，不重问已知决策
- ✓ 若最近 WAL 显示验证未通过，先处理该阻塞
- ✗ 不应凭空总结任务历史而不读 WAL
