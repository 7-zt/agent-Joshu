# 报告与论断纪律

两类正式输出（事实-only 问题报告、调研报告）的模板与规则，以及所有输出共用的论断分类与来源分级纪律。

## 问题报告（事实-only）

记录发现的问题、bug、异常行为。**只记事实，不做分析**。报告供后续独立任务（排查、修复、评审）消费。

**核心原则**：事实与分析分离。报告阶段只记录可观测事实；定位、根因、方案留给后续任务。这防止过早收敛、减少认知偏差、保持报告客观。

### 模板

```markdown
# 问题：<简短描述性标题>

**报告时间**：YYYY-MM-DD HH:MM
**报告人**：<姓名或标识>
**严重程度**：<Critical/High/Medium/Low/待评定>（评定人 + 依据；不确定就写「待评定」）
**问题类型**：Bug / Performance / Deployment / Documentation / Other

## 当前状况
- 观测到的现象（何时、何地、影响范围），只描述不解释。

## 预期行为
- 期望的正确行为。

## 复现步骤
1. …
**复现情况**：<每次 / 偶尔（约 x/y 次）/ 仅一次 / 未尝试复现>

## 环境信息
- 来自实际命令输出的版本信息，按 evidence-and-snapshot 的快照字段采集；可裁剪，无关项写「不适用」。

## 日志与错误信息
- 完整关键片段，保留时间戳与上下文；脱敏后写入。

## 已尝试的操作
- 尝试 A：<实际结果>（只记结果，不记判断）

## 附加信息
- 其他相关观测事实。
```

### 规则

- 只记录可观测、可重现、可验证的事实；错误信息不截断关键部分。
- 版本信息来自实际命令输出，不猜测。
- 复现步骤可操作；未尝试复现就如实写「未尝试复现」。
- 缺失信息写「待补充」，不编造。
- **绝对禁止**：推测性语言（「可能」「应该是」「估计」）、根因分析、解决方案建议、代码修改建议。
- 模板按问题类型可裁剪：不适用的节写「不适用」，不制造内容。
- 报告独立可读，不依赖会话上下文。
- 存储位置：默认写入工作区 `reports/` 目录，文件名 `YYYY-MM-DD-NN-theme.md`（NN 从 01 递增）。项目另有约定（如任务材料目录）时从其约定。

## 调研报告

结构化、证据优先调研的输出（调研流程见 workflow/consult.md 调研轨）。要点：先宽后深、多源交叉验证、未解决问题显式记录。

### 来源分级

1. **一手来源**：官方文档、论文、发布页、项目源码与官方 issue、直接实验与测量结果。
2. **二手来源**：技术博客、教程、社区讨论、行业报告——只用于发现线索、补充背景、辅助对比。
3. **仅作线索**：营销材料、来源不明内容。

优先一手；二手不单独支撑结论。

### 来源快照（审计链）

重要来源**默认保存快照**：原文存为 Markdown 文件（含 URL、作者、发布日期、访问日期）。无法保存原文时，至少保存：详细摘要、关键摘录、URL、作者、发布日期、访问日期。快照归档到报告的 `sources/` 子目录，正文引用快照路径。不依赖网页当前状态做后续审计。

### 论断分类（输出中逐条标注）

- **[事实]**：可直接验证的客观陈述（版本号、API 存在性、功能特性）。
- **[推断]**：基于事实的推导，给出推理链。
- **[判断]**：主观评价或权衡（「X 更适合场景 Y」）。
- **[宣传]**：利益方的营销性陈述（「最快的推理引擎」）——引用时必须保持此标注。
- **[未解决]**：当前证据不足或冲突的问题。

### 输出骨架

```markdown
# <调研主题>
调研时间 / 调研目的 / 关键维度

## 执行摘要（3-5 段核心发现，按重要性）

## 主要发现
### <维度>
[事实]… [推断]… [判断]…
来源: [标题](快照路径或URL) - 访问日期/版本

## 对比与权衡（如适用）

## 未解决问题
1. <问题> - 原因：证据不足 / 证据冲突 / 版本不明

## 来源清单（按一手/二手/仅线索分级）

## 建议后续行动（如适用）
```

### 证据要求

- 重要论断引用来源（URL + 访问日期，或文档版本/快照路径）。
- 版本相关功能与行为必须标注版本号；版本不明写「版本未确认」。
- 性能数据注明：测量环境、负载、来源、是否官方数据、是否本机复测（满足 benchmark-protocol）。
- 对比结论说明对比维度与适用条件。
- 证据冲突不隐藏，记入未解决问题。
