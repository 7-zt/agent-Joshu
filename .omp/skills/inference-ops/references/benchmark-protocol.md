# Benchmark 协议与测量质量

本文是 inference-ops 全部数字断言的证据标准：任何性能数字事后可审计、可复现、可判定置信度。第一部分规定记录什么；第二部分解释为什么那样记录、如何避免测量伪影、如何判断差异是真实的还是噪声。

## 一、Benchmark 协议

### 1. 负载定义（每次测量必填）

| 字段 | 说明 |
| --- | --- |
| 模型与精度 | 模型名、量化方案（如 FP16 / AWQ-INT4 / FP8）、推理引擎与版本 |
| 输入/输出分布 | 输入长度分布、输出长度分布或上限（ISL/OSL），不是单一「平均」值时给出分布描述 |
| 并发/到达模型 | 固定并发数或到达率（RPS），及客户端位置（同机/跨机、网络路径） |
| 请求量或时长 | 总请求数或持续时间；warmup 请求数（不计入统计） |
| 随机性与缓存 | 随机种子（如适用）、是否共享前缀、缓存冷/热状态 |
| 数据集 | 数据来源（合成/真实）、生成方式 |

缺字段的测量结果标记「负载定义不完整」，其数字不得用于对比结论。

### 2. 环境记录（每次测量必填）

- 硬件：GPU 型号与数量、拓扑（NVLink/PCIe）、CPU、内存、磁盘类型。
- 软件：驱动版本、CUDA runtime/toolkit、容器 runtime 与镜像 digest（如适用）、引擎版本或 commit、关键启动参数。
- 采集命令留痕：环境信息必须来自实际命令输出（如 `nvidia-smi`、`nvidia-smi topo -m`、引擎 `--version`），记录命令文本与输出摘要，不得凭记忆填写。
- 秘密脱敏：环境变量与配置中出现的 token、密钥、私有地址必须脱敏后才能写入报告。

### 3. 统计口径

**两级分开，不混用：**

1. **请求级分布**（单次运行内）：对每个指标收集全部请求的样本，报告 P50/P95/P99 需要足够样本量；样本量随数字报告。适用指标：TTFT、TPOT/ITL、端到端延迟。
2. **跨运行统计**（多次运行间）：重复完整运行（建议 ≥3 次，报告实际次数），对每次运行的汇总值（总吞吐、P99 等）报告均值、标准差或中位数、原始运行列表。改进小于跨运行波动时不得宣称为提升。

按指标选择合适的统计量，不强制每个数字同时报告全部统计量；但必须报告样本数。

### 4. 最小结果集

按适用性报告：吞吐（tokens/s 或 requests/s）、TTFT、TPOT/ITL、端到端延迟、错误率、资源利用率（GPU util、显存峰值、功耗）、以及适用时的质量/精度回归口径（如困惑度、下游任务分数、人工抽查）。

### 5. A/B 对比规则

- **单变量原则**：一次对比只改一个目标变量（参数、版本、配置项）；其他环境必须一致。无法一致的项必须列为「混杂因素」并出现在结论的不确定性说明中。
- 基线与改后各自满足第 1-4 节的完整证据集。
- 结论报告效应量与跨运行波动的关系；无法区分时写「在当前样本量下无法与噪声区分」。

### 6. 快速模式的放宽

快速模式允许：

- 输出「待验证假设」与建议采集命令，而不完成完整测量；
- 引用外部基准数字（官方/第三方）作为线索，但必须标注来源、版本、「未本机复测」。

快速模式不允许：输出已证实的瓶颈结论、已证实的收益数字、确定的参数行为断言（版本不明时）。

### 7. 归档

测量结果与原始数据（日志、脚本、汇总表）归档到当前任务材料或报告目录，报告引用归档路径。只有会话内的数字不进入正式报告。

## 二、测量质量

### 核心模型

性能测量值 = 真实值 + 系统性偏差 + 随机噪声

**系统性偏差**：测量方法本身引入的固定偏移（冷启动、客户端瓶颈、计时器精度）。多次运行不能消除，需要设计消除。

**随机噪声**：每次运行的不可预测波动（调度、后台任务、硬件状态）。多次运行可通过统计量化，但不能消除到零。

### 主要误差来源

**1. 冷启动 vs 稳态**：首次请求比后续慢 10-100 倍（模型加载、JIT 编译、缓存预热、连接池建立）。处理：warmup 阶段发足够请求让系统进入稳态（观测延迟稳定），丢弃 warmup 数据；分别测量冷启动与稳态，不混合报告；声明测的是哪个。常见误判：把包含冷启动的测量当稳态吞吐。

**2. 时钟与采样精度**：亚毫秒操作测出来都是 0ms 或 1ms（Linux 默认 1ms，Windows 可能 10-15ms）。处理：微秒级操作重复 N 次取总时间除以 N，或用高精度计时器（`clock_gettime(CLOCK_MONOTONIC)`、`QueryPerformanceCounter`）；纳秒级用硬件性能计数器（`perf`、`rdtsc`）；声明计时器类型与精度。常见误判：把精度不足的测量当真实分布。

**3. 背景负载与资源竞争**：同一测试不同时间跑结果差 2-5 倍（其他进程、系统服务、定时任务、共享机器租户）。处理：理想是专用机器、关闭不必要服务、固定 CPU 绑核；现实是多次运行、报告方差、标注共享环境；对比时保持环境一致。常见误判：单次运行下结论。

**4. 热节流（Thermal Throttling）**：长时间测试中性能逐步下降 10-30%（GPU/CPU 温度达阈值自动降频）。处理：监控温度与频率（`nvidia-smi dmon`、`watch -n1 cat /proc/cpuinfo`）；测试间等待温度回基线；改善散热或接受节流作为真实工况；报告是否出现节流。常见误判：把节流后的低性能当稳定状态。

**5. 数据生成偏差**：测试数据上快、真实数据上慢（测试数据过于规整，真实数据有长尾、罕见模式、缓存未命中，输入长度分布不匹配）。处理：从真实流量采样或按真实分布生成；报告数据特征（长度分布、词表覆盖、模式种类）；分别测不同输入特征下的性能。常见误判：用 512 token 固定输入测长文本系统。

**6. 客户端瓶颈**：服务端 GPU 利用率低，延迟却高（客户端并发不足、客户端 CPU 成为瓶颈、网络往返混入应用延迟）。处理：分离网络 RTT 与服务端处理时间；增加客户端并发到服务端利用率饱和；用多台客户端或异步发送；服务端埋点分离各阶段。常见误判：把端到端延迟当服务端处理时间。

**7. 缓存效应**：第二次跑比第一次快 10 倍（文件系统缓存、KV cache 预填充、权重常驻显存）。处理：声明缓存状态（cold/warm/hot）；测试前清缓存（`sync; echo 3 > /proc/sys/vm/drop_caches`）或预填充；分别测各缓存状态；真实工况往往是 warm。常见误判：把 hot cache 当 cold 报告。

### 统计有效性

**样本数最低要求**：

- 延迟：至少 3 次独立运行，报告中位数与 P95/P99。
- 吞吐：至少 5 次独立运行（每次足够时长达稳态），报告均值与标准差。
- 微观 benchmark（单操作）：至少 10 次。

**判断是否足够**：变异系数 CV = 标准差 / 均值。CV < 5% 样本足够；CV 5-10% 边缘可接受，增加样本更好；CV > 10% 噪声过大，增加样本或改善环境。

**A/B 对比的显著性**——改动后性能变化是真实的还是噪声？

简单判断（样本数少时）：两组各至少 5 次运行；画箱线图或列出各次测量值；两组四分位范围（Q1-Q3）不重叠 → 差异明显；重叠但中位数差 > 较小组的四分位距 → 可能有差异；重叠且中位数差小 → 不确定，需更多样本。

正式判断（有统计工具）：Mann-Whitney U 检验（非参数，适合延迟分布）；t 检验（要求正态，适合吞吐均值）；p < 0.05 视为显著，但要报告效应量。

常见误判：单次对比下结论；只看均值不看分布；差异小于测量噪声时宣称「提升 X%」。

**实际效应 vs 统计显著性**：统计显著 = 差异不太可能是随机的（p 值）；实际效应 = 差异大到值得在乎。示例：测 10000 次后延迟从 50.00ms 降到 49.95ms，p < 0.001（统计显著），但实际效应 0.1% 可忽略。反例：测 3 次从 100ms 降到 70ms（30%），但 p = 0.15（不显著）——实际效应大，需更多样本确认。报告时同时给统计结论与效应大小。

### 正反例

**好的测量设计**：

```text
目标：对比量化方法 A vs B 对吞吐的影响

设计：
- 环境：单 A100-80GB，CUDA 12.1，vLLM 0.4.2，模型 Llama-2-7B
- 负载：输入 512 token，输出 128 token，并发 32（已验证饱和）
- Warmup：50 请求后开始计时
- 采集：每种方法跑 10 次，每次 500 请求
- 控制：两种方法间清 KV cache，重启服务
- 测量：服务端日志的处理时间（排除网络）

结果：
- 方法 A：均值 45.2 tok/s，标准差 1.8 tok/s，CV 4.0%
- 方法 B：均值 52.7 tok/s，标准差 2.1 tok/s，CV 4.0%
- Mann-Whitney U：p < 0.001，效应 16.6% 提升
```

清晰、可复现、控制变量、统计足够。

**坏的测量**：「优化后快了 3 倍」——没说基线环境、测了几次、负载；3 倍是什么指标；可能是冷启动 vs 稳态的对比。不可复现、无法验证。

### 常见误判模式

1. 「理论上能达到」：计算出的峰值当实测结果。
2. 单次运行当结论：忽略随机噪声。
3. 混合冷启动与稳态：把瞬态当常态。
4. 改多个变量：同时改模型、batch size、量化方法，无法归因。
5. 客户端瓶颈误判服务端慢：端到端延迟全算服务端。
6. 精度不足当零开销：亚毫秒操作测成 0ms。
7. 不报方差：只报均值或单次峰值。
