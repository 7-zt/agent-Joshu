# summarizer：会话蒸馏 Q&A 知识库

把本项目内三家 agent 会话里「值得日后复习的知识问答」蒸馏成项目根 `QA.md` 的条目，严格按会话发生的时间顺序追加，只增不改。这是给用户本人看的长期学习记录：任务过程的记录另由项目的任务记录机制负责，服务 agent 完成工作；本 Skill 服务用户回看、加深理解。

## 何时用

- 仅当用户显式输入 `/skill:summarizer` 时运行。本 Skill 不隐式触发：它读写用户的知识库、要通读大量会话，成本与影响都应由用户掌握。
- 适用场景：学习型项目（用户在此用大模型学习、调研理论或专业内容），用户想把手上的会话收进一份可复习的 Q&A。
- 不适用：纯工程排障项目（问题属于任务过程，由项目的任务记录机制负责）；单次琐碎问答。

## 维护对象

- 文件：项目根 `QA.md`（`cwd` 即项目根）。
- 语言：中文。
- 排序：严格按知识发生的时间，不是运行日期。条目日期取该问答所在轮次的时间戳（dump 中该轮的 `===` 头），同一会话里的多条可各占各的日期；同轮内多条按对话顺序。处理会话时按开始时间先后逐个蒸馏，追加自然保持时间序。
- 只能追加：发现旧条目有误，用纠错标记标出，新内容追加在后；不改写历史条目正文。
- 文件头仅在首次创建时写入：三五行说明本文件用途、只能追加、纠错靠标记加后补。

## 运行流程

运行主体是当前 OMP 会话，`extract.py` 只负责扫描与导出人话对话。

1. 确认项目根（当前 `cwd`），`QA.md` 位于项目根。
2. 运行 `python <本 Skill 目录>/scripts/extract.py new`，得到本项目下新增或有变更的会话，已按开始时间排好序。输出为空则报告「无新会话」后结束。
3. 通读 `QA.md`（存在时），作为去重与修正的判断基准。
4. 逐会话运行 `python <本 Skill 目录>/scripts/extract.py show <session_id>`，读导出的对话文本：挑出知识性问答（概念、原理、为什么、技术解释），纯任务操作（改代码、跑命令）不选；「用户复述自己的理解 + AI 确认或纠正」是最高价值信号，优先记录。
5. 起草条目 → 与 `QA.md` 语义去重 →（如有）标记旧条目 → 按轮次时间顺序追加到文件末尾。
6. 追加成功后运行 `python <本 Skill 目录>/scripts/extract.py done`，提交本次指纹。
7. 汇报：扫描 N 个会话、新增 M 条、标记 K 处修正。

`extract.py` 子命令：

- `new [--project PATH]`：列出本项目下新增/变更会话，每行一个 JSON（`agent`/`session_id`/`file`/`started`/`size`/`mtime`），按 `started` 排序。`--project` 默认当前目录。
- `show <session_id> [--project PATH]`：把该会话人话对话写入系统临时目录的 dump 文件并打印其绝对路径。
- `done [--project PATH]`：全量重写 `.agents/summarizer-state.json` 中本项目的会话指纹。

增量机制：状态文件是项目根 `.agents/summarizer-state.json`，指纹为「文件大小 + 修改时间」。文件增长（长会话被续写）会重新出现在 `new` 里，重提一遍即可；由 `done` 提交后不再重复。

## 条目格式

条目格式：

    ## YYYY-MM-DD · <omp|claude|codex> · <问句作标题>

    （两三段正文，自包含：不回开原会话也能读懂）

    > 来源：claude session 84ff8f23

样例（含用户复述理解被纠正的情形）：

    ## 2026-10-14 · claude · 为什么 KV Cache 能加速自回归解码

    自回归生成每一步都只多一个 token，但注意力要回头看过往所有 token。没有缓存时，第 t 步会把前 t 个 token 的 K、V 重算一遍，计算量随序列长度平方增长。KV Cache 把每一步算出的 K、V 存下来，下一步直接复用，只新算当前 token 的 K、V——计算量降到线性，代价是显存占用随上下文长度线性上涨。

    我当时理解成「缓存的是 attention 输出」，实际缓存的是每一层的 K 和 V 矩阵，attention 输出并不存。区别在于：存 K、V 才能跳过投影计算，存输出则省不掉。

    > 来源：claude session 84ff8f23

格式要点：

- 标题就是问题本身（问句），不是概括性标签。
- 正文融合书写，不保留原始对话顺序：用户理解被确认 → 直接作为答案主干；被纠正 → 保留「我当时理解成 X，实际是 Y」的误解对照（复习价值最高）。
- 条目末尾附来源行，便于跳回原文。

## 纠错标记

- 旧条目末尾追加一行引用块（原正文一字不改）：

    > ⚠ YYYY-MM-DD 修正：本条有误，见下方同日条目

- 新条目开头注明修正对象（例如「修正上条 2026-10-14 的 KV Cache 说明」）。
- 只用标记加后补，不改写旧条目正文。

## 去重与修正规则

- 同一问题指语义相同，不是字面相同：换措辞、中英文差异、详略不同都算同一问题，由模型判断。
- 同一问题已记且无新信息 → 跳过，不新增。
- 后续会话加深或修正了理解 → 视为新条目追加（时间线记录认知成长，不合并不覆盖）；若修正了旧条目结论，同时对旧条目加纠错标记。

## 写作规则

条目正文遵循以下最小规范（已内联到本 Skill，不依赖其他文档）：

- 具体：写事实与机制，不堆抽象修饰；每句话能重述成指令、事实或数字，否则删。
- 一句一个意思；主动语态；平实动词，不用「进行、赋能、抓手、闭环、拉通、对齐」。
- 去 AI 腔：不用「重要的是」「不仅仅是 X 更是 Y」「值得注意的是」，不强迫三段式，不频繁加粗，不堆破折号、装饰 emoji、滥用引号。
- 中文为主，术语首次出现附英文。
- 标题就是问题本身，不是概括性标签。

## 失败处理

- `extract.py` 报错或退出码非零：把原始错误贴给用户，停下，不猜测替代命令。
- 某来源目录缺失（如本机没有 codex 会话）：该来源为空，属正常，不报错；照常处理其余来源。
- `new` 无输出（无新会话）：报告「无新会话，QA.md 未改动」后结束。
- `show` 找不到会话：确认 `session_id` 拼写与本项目匹配（`show` 只在当前项目范围内查找）。
