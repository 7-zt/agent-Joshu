# 测试

## 目标

测试验证被测对象对外呈现的行为。优先断言输入、输出、可观察状态变化和错误结果，不断言私有方法、内部临时状态或具体实现步骤。

## 边界

- API 测试围绕请求和响应。
- 组件测试围绕输入和输出。
- 流程测试围绕最终可观察结果。

测试边界确定后，断言只围绕该边界展开。测试目标视为黑盒。

## 组织

- 目录按测试层级和领域组织：`tests/<domain>/test_*.py`。
- 同一文件按主题、场景或能力连续组织，不按编写时间堆叠。
- 单步行为与多步流程分开，基础行为与联动场景分开。
- 参数化只覆盖同一接口、同一主题的多组输入。不同端点或不同主题拆成独立测试。

## 命名

- 测试文件和函数使用 `test_` 前缀。
- 函数名简洁，最多 40 字符，只表达主题。
- 细节放入文档字符串，不塞进函数名。
- 每个测试函数写中文文档字符串，说明验证的行为和预期结果。
- 同一文件内命名和文档字符串风格保持一致。

## fixture

fixture 提供可复用的基础对象，例如默认上下文、默认配置、输入容器或种子数据。不要在 fixture 中提前封装具体业务语义，场景变化在测试体内构造。

辅助函数和 fixture 有理解成本。重复较少时保留局部重复；至少三处有相同逻辑且抽象后更容易理解时，再提取公共部分。

## 断言

- 使用直接、清楚的断言，优先断言状态码、返回字段和可观察结果。
- 每个测试有一个主要目标，多个断言共同服务于同一件事。
- 不混合多个主题。
- 不依赖内部状态、私有字段或实现细节。
- 错误场景断言明确的异常或失败结果。

## 覆盖

一组完整测试通常覆盖：

- 正常路径。
- 边界输入。
- 不存在或失败路径。
- 多次调用或联动场景。

覆盖率用于判断完整性，不用于制造脆弱测试。只为覆盖某一行、且必须依赖内部细节的测试通常得不偿失。非核心语句、临时分支和语法兼容分支可以使用 `pragma: no cover`。

## 检查

提交前由 `git commit` hooks 运行 pytest。需要单独复现时使用：

```bash
uv run --no-sync pytest -q
```

测试失败时先确认断言是否绑定实现细节。测试依赖未确认的内部行为时，按外部行为调整测试，不改变对外行为来迁就测试。
