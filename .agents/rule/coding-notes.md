# 工程笔记

## 优先简单

先选满足目标、正确且整体复杂度最低的方案。不要为假想需求增加中间层、配置项或兼容路径。

简单不是少写代码，而是让读者能沿着数据流和调用链理解系统。需要解释很久才能看懂的「精巧」实现，通常不适合长期维护。

## 警惕过早抽象

两个实现相似，不代表需要抽公共父类或通用框架。抽象应来自稳定的共同契约，而不是当前代码长得像。

出现以下信号时再考虑抽象：

- 至少三处有相同逻辑，且变化方向一致。
- 抽象后的接口比重复代码更容易理解。
- 调用方不需要了解实现细节就能正确使用。

## 控制依赖方向

依赖应该指向稳定的一方，不让底层工具反向依赖 HTTP、插件入口或具体模型。

跨模块共享时先确认公共面：只暴露调用方真正需要的符号，私有实现留在模块内部。

## 让失败可见

错误应该尽早暴露，并带上足够定位的上下文。静默回退、吞异常和「先继续跑」会把问题推迟到更难排查的位置。

只有需求明确要求降级时才降级，并记录降级原因和影响范围。

## 先验证再扩展

修改行为前先确认当前行为。能用最小复现说明问题，就不先读完整模块；能用一个断言证明结果，就不先搭建测试框架。

验证针对已给出的结论，不为了「顺手看看」扩大范围。
