# ADR 决定：项目自含与 bootstrap

反向决定：2026-09-21-master-kit-and-project-contexts.md（其中「Python 单命令安装器——被拒」一条；该决定的其余规则——双层架构、记录策略、ADR 生命周期——仍有效，由本决定延续并扩展部署单元语义）

## 背景

2026-09-22 评审（grill.md 评审记录 3）：用户 SSH 轮换多设备开发，「部署单元＝设备」的工具包与设备严格绑定，与可移植初衷不符。用户哲学：主包自身维护可以复杂，但作为工具包应用到别的项目时应灵活、轻量、好操作。部分目标设备为内网机（不能联网），离线安全是硬约束。2026-09-21 否决安装器时主包还是纯文档仓库；现主包含代码组件（memtrace CLI），一条 bootstrap 命令的成本结构已变。

## 决定

- **部署单元＝项目**：主包＝复杂源仓（维护成本留在主包侧）；项目＝自含轻量包。新项目用 `memtrace bootstrap <目标项目路径>` 一条命令装入完整工具包子集（模板 agent-joshu/ + skills → `.omp/skills/` + memtrace 包 → `agent-joshu/memtrace/` + OMP 扩展 → `.omp/extensions/memtrace/`），默认全量 8 个 Skill，`--skills` 过滤备用。
- **离线硬约束**：bootstrap 纯本地复制，零网络调用；工具包传输与项目代码同渠道（项目怎么到内网机，工具包就怎么到）。
- **更新语义**：幂等重跑＝比对更新；项目自有内容（`agent-joshu/adr/` 生命周期文件、已并入根 AGENTS.md 的段落、用户改过的 kit 文件）永不覆盖，只报告漂移；冲突写 `.new` 不覆盖。
- **OMP 扩展优先项目内 CLI**：扩展发现 `<项目>/agent-joshu/memtrace/` 存在时优先以项目内 vendored CLI 运行，主包路径退为后备（主包内自用与旧项目兼容）。
- **主开发机双模式并存**：全局加载（customDirectories 指主包 skills/）与项目自含（`.omp/skills/`）并存；双源同名行为实测记录，冲突时回退为统一 vendored 或解除全局配置。

## 真实替代项

- 项目半自含（现状加强：技能仍走设备侧 omp config）——被拒：保留设备绑定，与可移植初衷不符。
- 设备侧插件化（主包做成 omp 插件包，`omp install` 一条命令）——被拒（降级为未来项）：内网机不能联网拉取；且技能能否随插件分发未验证。重审条件：全部目标设备可联网。
- git subtree 每项目携带主包全量——被拒：每项目背全部源仓内容（含 reports/、评审记录等非工具包内容），更新靠 subtree pull，噪声大于收益。
- 嵌套 git clone（2026-09-21 Shape B）——维持被拒：决策记录无法随项目 git 走。

## 后果

- ✓ 新项目一条命令接入；项目 clone 到任意设备（含内网机）即得全部能力，仅需 OMP + Python 3.10+
- ✓ 主包维护复杂度（bootstrap 代码、manifest、双源兼容）全部留在主包侧，符合「项目应用要轻」哲学
- ✗ 每项目 vendored ≈1.4M/约 160 文件噪声（接受，S9 实测）
- ✗ 更新靠重跑 bootstrap 比对（接受；漂移报告兜底）
- ✗ 内网机上联网型 Skill（如 deep-research 的 web 采集）降级不可用（用户明示接受）
- ✗ 主开发机双源同名 Skill 加载行为待实测（S10）；冲突时回退任一皆可接受

## 重审条件

全部目标设备可联网时（重审插件化 omp install）；vendored 体积成为实际负担时（重审子集默认）；OMP 上游改变 `.omp/skills/` 项目级自动发现行为时（重审分发通道）。

## 变更

### 2026-09-22 删除「主开发机双模式并存」子句

设备维度整体废止（见 2026-09-22-project-level-skills-auto-discovery.md）：项目级 `.omp/skills/` 自动发现为唯一技能机制，主包 skills/ 已 `git mv` 至 `.omp/skills/`，主开发机全局加载与双源并存场景不复存在。其余条款（部署单元＝项目、bootstrap 语义、离线硬约束、更新语义）不变；「OMP 扩展优先项目内 CLI」条款不变。
